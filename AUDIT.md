# Аудит кода — ЗАРЯД (табель учёта рабочего времени)

> **Важное замечание перед отчётом.** Запрошенный шаблон аудита рассчитан на лендинг (HTML/CSS/JS, вёрстка, SEO/производительность фронта). Фактически это не лендинг, а серверное веб-приложение на Python (stdlib `http.server`, без фреймворка и сборщика) с HTML, который генерируется прямо в Python-коде через `.format()`-шаблоны, плюс SQLite-база. Публичной посадочной страницы с формой заявки/лендинг-конверсией в проекте нет — это внутренний инструмент учёта рабочего времени за логином (роли admin/accountant/worker).
>
> Ниже отчёт адаптирован под то, что есть в репозитории: секции 1–3, 5–6 сохранены по смыслу запроса, но применены к реальному стеку. Раздел про безопасность добавлен отдельно, потому что при аудите всплыли критичные проблемы именно там — обходить их молчанием было бы неправильно.

## Статус: что исправлено по итогам аудита

Все находки ниже, кроме двух явно помеченных, **исправлены и проверены вживую** (поднимался тестовый сервер на временной БД, воспроизводились те же запросы/сценарии, что и при обнаружении). Прод-база `data/worktime.db` не затрагивалась.

- 🟡 «Cookie сессии без флага `Secure`» — не включено, так как сайт сейчас работает по обычному `http://` без reverse-proxy с TLS; включение `Secure` сломало бы логин. Вернуться к этому, если появится HTTPS-прокси.

**Исправлено:**
- 🔴 Reflected XSS через `period`/`from`/`to` — экранирование + allowlist-валидация.
- 🔴 Роль «бухгалтер» видела пароли работников — доступ к `/workers`, `/objects` и связанным API закрыт.
- 🟡 Нет защиты от подбора пароля — добавлен лимит попыток (5 за 5 минут).
- 🟡 «Запомнить на 30 дней» не работало — чекбокс теперь реально влияет на срок сессии и cookie (заодно поправлен смежный баг: у cookie отсутствовал `Max-Age`).
- 🟡 CSV/Excel-инъекция через имя работника и поиск — экранирование ведущих `=+-@`.
- 🟡 Логирование запросов было отключено — включено, пишет в `logs/access.log` с ротацией.
- 🟡 Необработанные исключения на невалидном `int()` в API — обёрнуты, теперь чистый `400` вместо обрыва соединения.
- 🟡 Нет WAL-режима SQLite — включён.
- 🟡 Chart.js с CDN без версии/SRI — скачан и захостен локально (`static/chart.min.js`, версия 4.4.4, вынесен из `<head>` в конец страницы).
- 🟡 Автообновление дашборда каждые 30 сек сбивало ввод — теперь не перезагружает страницу, пока фокус в поле ввода.
- 🟢 Дублирование `showToast`/`switchTab`/поиска в 6 файлах — вынесено в `static/app.js`.
- 🟢 Дублирование `.tabs` в CSS — убрано.
- 🟢 Дублирование подсчёта статистики в CSV/Excel экспорте — вынесено в `_build_stats()`.
- 🟢 Отсутствие `aria-label` — добавлен на кнопку «Наверх».

## 1. Структура проекта

**Стек:** Python 3.10+, stdlib `http.server.ThreadingHTTPServer` (без Flask/Django/FastAPI), SQLite (`sqlite3`), один внешний пакет — `openpyxl` для экспорта в Excel. Фронтенд — ванильный JS, инлайн в Python-строках (общие функции теперь вынесены в `static/app.js`), общий CSS-файл. Сборщика/бандлера, npm, TypeScript, Jinja2 — ничего этого нет; HTML собирается ручными f-строками и `str.format()`.

```
app.py              — точка входа: миграции БД, поток очистки сессий, поток бэкапов, логирование, запуск сервера
config.py           — .env, DB_PATH, HOST/PORT, TZ, TTL сессий
utils.py            — время, периоды, расчёт часов/опозданий, валидация period/date
sessions.py         — сессии в памяти (dict + threading.Lock), лог входов
login_throttle.py   — лимит попыток логина
manage_admins.py    — CLI управления пользователями

db/                 — доступ к SQLite, по одному модулю на сущность (workers, shifts, objects,
                       attachments, credentials, admin_users, comments, audit, login_log, backup)
views/              — генерация HTML на каждую страницу (шаблон + JS инлайн в одном файле)
handler/            — маршрутизация: base.py (общие хелперы), get_routes.py, post_routes.py
static/
  style.css         — стили
  app.js            — общие JS-функции (showToast, switchTab, поиск)
  chart.min.js      — самостоятельно захостенный Chart.js 4.4.4
```

Ключевое архитектурное наблюдение (актуально по-прежнему): **HTML, CSS и JS не разделены** — каждый файл в `views/` содержит Python-строку с полным HTML-документом, включая `<script>` с логикой конкретной страницы. Общие JS-утилиты вынесены в `static/app.js`, но сама вёрстка каждой страницы (таблицы, модалки, разметка) по-прежнему живёт внутри Python-файла. Полноценный переход на шаблонизатор (Jinja2 и т.п.) с автоэкранированием — более крупный рефакторинг за рамками этого прохода, но именно отсутствие автоэкранирования стало причиной найденного XSS.

## 6. Ошибки, баги и безопасность

### 🟢 [ИСПРАВЛЕНО] КРИТИЧНО: Reflected XSS через параметры `period`, `from`, `to` на дашборде

Было подтверждено запросом `GET /?period=%22%3E%3Cscript%3Ealert(1)%3C/script%3E` — инъекция срабатывала в трёх местах ответа одновременно.

Исправлено на двух уровнях (defense in depth):
1. **Валидация на входе** — [handler/get_routes.py](handler/get_routes.py): `period` пропускается через `safe_period()` (allowlist из `PERIOD_LABELS`), `from`/`to` — через `safe_date_str()` (`dt.date.fromisoformat`, при ошибке — пустая строка). Функции добавлены в [utils.py](utils.py). Применено во всех трёх местах, где эти параметры читаются (дашборд, `/export`, `/export_xlsx`) — заодно закрыло потенциальную инъекцию в заголовок `Content-Disposition`.
2. **Экранирование на выходе** — [views/dashboard.py](views/dashboard.py): `period_label`, `period`, `cal_from`, `cal_to` теперь оборачиваются в `html.escape()` перед подстановкой.

Повторный запрос с тем же payload'ом после фикса — инъекция больше не отражается, `period` корректно откатывается на `week`.

### 🟢 [ИСПРАВЛЕНО] КРИТИЧНО: Роль «бухгалтер» могла видеть пароли всех работников

[handler/get_routes.py](handler/get_routes.py) — добавлена проверка: `if is_accountant_role and path not in ("/export", "/export_xlsx"): 403`. Теперь бухгалтер видит только дашборд и может скачать Excel/CSV — как и написано в README. Заодно убрана свежерастворившаяся дублирующая проверка `is_accountant_role` внутри блока `/users` (стала недостижимой после общей проверки).

Проверено вживую: аккаунтом с ролью `accountant` — `/workers` → 403, `/objects` → 403, `/users` → 403, `/` → 200, `/export_xlsx` → 200. Пароль работника больше не виден бухгалтеру ни при каком запросе.

### 🔴 ОТЛОЖЕНО (по решению пользователя): Пароли хранятся в открытом виде

Не тронуто. При обсуждении договорились не переходить на хэширование пароля прямо сейчас, так как это меняет UX: страница `/workers` сейчас показывает пароль работника постоянно, открытым текстом, а с хэшированием так делать нельзя в принципе — пароль можно было бы показать только один раз, сразу после создания/сброса.

**Если решите вернуться к этому:** переход на `hashlib.scrypt` (без новых зависимостей) для `admin_users.password_plain` и `worker_credentials.password_plain`, замена сравнения в `authenticate_admin` на `secrets.compare_digest` (сейчас там обычное `==`, у `authenticate_worker` это уже сделано правильно), плюс изменение `views/workers.py`, чтобы показывать пароль только сразу после `create_or_reset_worker_credential`.

### 🟡 ОТЛОЖЕНО (по решению пользователя): Cookie сессии без флага `Secure`

Не тронуто — сайт сейчас работает по `http://` без reverse-proxy с TLS, включение `Secure` сломало бы установку/отправку cookie браузером. Вернуться к этому, если появится HTTPS-терминация перед приложением.

### 🟢 [ИСПРАВЛЕНО] Нет защиты от подбора пароля (brute-force)

Добавлен [login_throttle.py](login_throttle.py): не более 5 неудачных попыток на логин за 5 минут, дальше — сообщение «Слишком много неудачных попыток» вместо попытки проверки пароля. Подключено в [handler/post_routes.py](handler/post_routes.py) `_handle_login`. Проверено: после 5 неудачных попыток даже верный пароль отклоняется с этим сообщением.

### 🟢 [ИСПРАВЛЕНО] «Запомнить на 30 дней» — чекбокс ничего не делал

[handler/post_routes.py](handler/post_routes.py) — `remember` теперь читается из формы: отмечен → сессия на `SESSION_TTL_DAYS` (30 дней), не отмечен → `SESSION_TTL_SHORT_DAYS` (1 день). Заодно исправлен смежный баг: у самой cookie не было `Max-Age`, из-за чего браузер трактовал её как «сессионную» (удаляемую при закрытии окна) вне зависимости от серверного TTL — теперь `Max-Age` в cookie соответствует выбранному сроку. Проверено: `remember=1` → `Max-Age=2592000`, без `remember` → `Max-Age=86400`.

### 🟢 [ИСПРАВЛЕНО] CSV/Excel-инъекция (formula injection)

[views/export.py](views/export.py) — добавлена `_csv_safe()`: если значение (имя работника или поисковый фильтр) начинается с `=`, `+`, `-` или `@`, перед ним добавляется `'`, чтобы Excel/Google Sheets не интерпретировали ячейку как формулу. Применено и в CSV, и в XLSX. Проверено: имя работника `=cmd|calc!A1` и фильтр `=SUM(1+1)` в экспортированных файлах превращаются в `'=cmd|calc!A1` / `'=SUM(1+1)` (текст, не формула).

### 🟢 [ИСПРАВЛЕНО] Логирование HTTP-запросов было полностью отключено

[handler/base.py](handler/base.py) — `log_message` теперь пишет через `logging` в `logs/access.log` (ротация 5 МБ × 3 файла, настроена в [app.py](app.py)). Папка `logs/` добавлена в `.gitignore`. Проверено: запросы реально появляются в файле с таймстампом, IP и статусом.

### 🟢 [ИСПРАВЛЕНО] Необработанные исключения на невалидном вводе в API

[handler/post_routes.py](handler/post_routes.py) — вызов обработчика в `do_POST` обёрнут в `try/except (TypeError, ValueError)`, возвращает `{"ok": false, "error": "Некорректные параметры"}` с кодом 400 вместо падения потока. Проверено: запрос с нечисловым `worker_id` теперь получает чистый 400, сервер продолжает работать.

### 🟢 Что сделано правильно — без изменений
SQL везде параметризован, защита от directory traversal в статике корректна, CSRF частично закрыт за счёт `Content-Type: application/json` + `SameSite=Lax`.

## Общий вывод

Из 3 критичных находок закрыты 2 (XSS, доступ бухгалтера к паролям); хранение паролей в открытом виде осталось сознательно — по решению пользователя, чтобы не менять текущий UX страницы работников без отдельного обсуждения. Все находки уровня 🟡 закрыты. Из 🟢-находок сделаны те, что имели чёткий безопасный fix (дедуп JS/CSS, aria-label); инлайн-стили и полный переход на шаблонизатор оставлены как более крупная работа на будущее.

**Не забыть, если решите продолжать:**
1. Хэширование паролей (`hashlib.scrypt`) — самая важная оставшаяся мера, требует согласования UX страницы `/workers`.
2. `Secure`-флаг на cookie — включить, как только появится HTTPS-прокси перед приложением.
3. Инлайн-стили → CSS-классы, полный переход на AJAX-обновление дашборда без `location.reload()` — необязательные улучшения без срока.
